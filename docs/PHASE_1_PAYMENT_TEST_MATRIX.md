# Phase 1 payment test matrix

Recorded 2026-10-07 (Asia/Calcutta). This is a test plan plus accurately scoped execution evidence. **No end-to-end payment case for the changed app has been runtime-tested on Android/Google Play.** No live orders, payments, refunds or provider bookings were created.

Mock tests run through Node's built-in runner and installed Babel; they execute helpers, hooks and screen handlers with fake SDK/network data. They do not establish the actual production response contract, Android activity behavior, provider funding, webhook processing or fulfillment. “Mock” below means automated evidence only; “Static” means code review only. No row claims an end-to-end PASS. See [architecture and validation](PHASE_1_CASHFREE_ARCHITECTURE.md).

Common acceptance rule: callback, HTTP 200, order creation, amount/date, first history row and local “Confirmed” defaults are never booking proof. Explicit payment success currently leads to PAYMENT_SUCCESS / BOOKING_PENDING. Automatic correlated confirmation requires backend support.

## Execution and remaining production acceptance

- Automated command: `node --test __tests__/payments.test.cjs`. Exact final count is recorded in the architecture document and final response.
- Expo Doctor, Android bundling and the debug Gradle build succeeded; these are not payment test passes.
- ADB found CPH2381 authorized in device state and the existing package installed by Google Play. An ADB launch intent reached its already-running activity. This was the prior installed build; the modified debug APK was not installed over it.
- The user's historical Play test removed the trusted-source error. The historical SRDV insufficient-balance error occurred before Cashfree order creation. Neither was retested here.
- Use a new Google Play-distributed test build for production Cashfree acceptance. Record app version/build, scenario, order reference in private backend evidence, callback count, normalized payment status, fulfillment status and navigation. Do not record JWTs, sessions, customer details or raw responses in this document.
- Backend must confirm order-status semantics, durable idempotency/recovery, safe error messages and reliable order-to-booking fulfillment correlation. Current local guards and retained route checkpoints do not guarantee exactly-once payment after process death, a wholly new route, reinstall or another device.
- Provider insufficient funds requires backend/provider operational resolution. Do not bypass it, spoof installer identity, patch integrity checks or switch environment to make a test pass.

Phase 1 stops at these changes and documented validation. Phase 2 has not started.
